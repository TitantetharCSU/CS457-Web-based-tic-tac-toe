# JSON-Based Tic-Tac-Toe Application Protocol Blueprint

## 1. Overview

This document defines the application-layer protocol for a two-player Tic-Tac-Toe game implemented over TCP.

The protocol uses:

* **TCP** for reliable, ordered communication.
* **JSON** for structured application messages.
* **Newline-delimited JSON (NDJSON)** for TCP message framing.
* A **server-authoritative game state**, meaning the server validates every move and determines the result of the game.
* Two players per game:

  * **Player 1** uses `X`.
  * **Player 2** uses `O`.

Every application message is represented as exactly one JSON object followed by a newline character (`\n`).

---

# 2. General JSON Message Format

Every message contains the following required fields:

| Field       | Type   | Description                                                |
| ----------- | ------ | ---------------------------------------------------------- |
| `type`      | string | Identifies the message type.                               |
| `game_id`   | string | Identifies the game/session.                               |
| `player_id` | string | Identifies the sender. The server uses `server` as its ID. |
| `payload`   | object | Message-specific data.                                     |

General structure:

```json
{
  "type": "MESSAGE_TYPE",
  "game_id": "game-001",
  "player_id": "player-001",
  "payload": {}
}
```

The `payload` object varies depending on the message type.

---

# 3. Message Types

The protocol defines the following message types:

1. `CONNECT`
2. `LOBBY_WAIT`
3. `GAME_START`
4. `MOVE`
5. `STATE_UPDATE`
6. `ERROR`
7. `GAME_OVER`
8. `DISCONNECT`

These messages provide enough information for clients and the server to establish a connection, wait for an opponent, start a game, exchange moves, report errors, finish the game, and terminate the connection.

---

## 3.1 CONNECT

### Direction

**Client → Server**

### Purpose

Requests that the server add the client to the Tic-Tac-Toe lobby.

The client sends this message immediately after establishing the TCP connection.

### Schema

```json
{
  "type": "CONNECT",
  "game_id": "string",
  "player_id": "string",
  "payload": {
    "player_name": "string"
  }
}
```

### Fields

| Field                 | Type   | Required | Description                                                     |
| --------------------- | ------ | -------- | --------------------------------------------------------------- |
| `type`                | string | Yes      | Must be `"CONNECT"`.                                            |
| `game_id`             | string | Yes      | Initially `"pending"` because a game has not yet been assigned. |
| `player_id`           | string | Yes      | Unique identifier generated by the client.                      |
| `payload.player_name` | string | Yes      | Human-readable player name.                                     |

### Example

```json
{
  "type": "CONNECT",
  "game_id": "pending",
  "player_id": "player-001",
  "payload": {
    "player_name": "Alice"
  }
}
```

# 3.2 LOBBY_WAIT

### Direction

**Server → Client**

### Purpose

Informs a client that the server accepted the connection but another player is still required before the game can begin.

### Schema

```json
{
  "type": "LOBBY_WAIT",
  "game_id": "string",
  "player_id": "server",
  "payload": {
    "players_waiting": "integer"
  }
}
```

### Fields

| Field                     | Type    | Required | Description                          |
| ------------------------- | ------- | -------- | ------------------------------------ |
| `type`                    | string  | Yes      | Must be `"LOBBY_WAIT"`.              |
| `game_id`                 | string  | Yes      | Assigned game identifier.            |
| `player_id`               | string  | Yes      | Always `"server"`.                   |
| `payload.players_waiting` | integer | Yes      | Number of players currently waiting. |

### Example

```json
{
  "type": "LOBBY_WAIT",
  "game_id": "game-001",
  "player_id": "server",
  "payload": {
    "players_waiting": 1
  }
}
```

The client remains connected and waits for `GAME_START`.

# 3.3 GAME_START

### Direction

**Server → Client**

### Purpose

Notifies both players that a game has been created and provides their assigned role and the initial board state.

### Schema

```json
{
  "type": "GAME_START",
  "game_id": "string",
  "player_id": "server",
  "payload": {
    "role": "string",
    "symbol": "string",
    "opponent_id": "string",
    "board": "array",
    "current_turn": "string"
  }
}
```

### Fields

| Field          | Type   | Description                               |
| -------------- | ------ | ----------------------------------------- |
| `role`         | string | Either `"PLAYER_1"` or `"PLAYER_2"`.      |
| `symbol`       | string | `"X"` for Player 1 or `"O"` for Player 2. |
| `opponent_id`  | string | ID of the opposing player.                |
| `board`        | array  | Nine-element board representation.        |
| `current_turn` | string | Player ID whose turn it is.               |

The board contains exactly nine elements corresponding to:

```text
0 1 2
3 4 5
6 7 8
```

An empty square is represented by `null`.

### Example sent to Player 1

```json
{
  "type": "GAME_START",
  "game_id": "game-001",
  "player_id": "server",
  "payload": {
    "role": "PLAYER_1",
    "symbol": "X",
    "opponent_id": "player-002",
    "board": [
      null,
      null,
      null,
      null,
      null,
      null,
      null,
      null,
      null
    ],
    "current_turn": "player-001"
  }
}
```

### Example sent to Player 2

```json
{
  "type": "GAME_START",
  "game_id": "game-001",
  "player_id": "server",
  "payload": {
    "role": "PLAYER_2",
    "symbol": "O",
    "opponent_id": "player-001",
    "board": [
      null,
      null,
      null,
      null,
      null,
      null,
      null,
      null,
      null
    ],
    "current_turn": "player-001"
  }
}
```

# 3.4 MOVE

### Direction

**Client → Server**

### Purpose

Requests that the server place the player's symbol in a specific board position.

The server is responsible for determining whether the move is valid.

### Schema

```json
{
  "type": "MOVE",
  "game_id": "string",
  "player_id": "string",
  "payload": {
    "position": "integer"
  }
}
```

### Fields

| Field              | Type    | Required | Description                          |
| ------------------ | ------- | -------- | ------------------------------------ |
| `type`             | string  | Yes      | Must be `"MOVE"`.                    |
| `game_id`          | string  | Yes      | Game being played.                   |
| `player_id`        | string  | Yes      | Player making the move.              |
| `payload.position` | integer | Yes      | Board position from `0` through `8`. |

### Example

```json
{
  "type": "MOVE",
  "game_id": "game-001",
  "player_id": "player-001",
  "payload": {
    "position": 4
  }
}
```

The server checks:

1. The game exists.
2. The player belongs to the game.
3. It is the player's turn.
4. The position is between `0` and `8`.
5. The position is currently empty.

If any check fails, the server sends an `ERROR` message and does not modify the board.

# 3.5 STATE_UPDATE

### Direction

**Server → Client**

### Purpose

Broadcasts the authoritative game board after a valid move.

Both players receive the same `STATE_UPDATE`.

### Schema

```json
{
  "type": "STATE_UPDATE",
  "game_id": "string",
  "player_id": "server",
  "payload": {
    "board": "array",
    "last_move": "object",
    "next_turn": "string"
  }
}
```

### Fields

| Field                 | Type    | Description                                    |
| --------------------- | ------- | ---------------------------------------------- |
| `board`               | array   | Current nine-element board.                    |
| `last_move`           | object  | Information about the move that was just made. |
| `last_move.player_id` | string  | Player who made the move.                      |
| `last_move.position`  | integer | Position that was selected.                    |
| `last_move.symbol`    | string  | `X` or `O`.                                    |
| `next_turn`           | string  | Player whose turn comes next.                  |

### Example

```json
{
  "type": "STATE_UPDATE",
  "game_id": "game-001",
  "player_id": "server",
  "payload": {
    "board": [
      null,
      null,
      null,
      null,
      "X",
      null,
      null,
      null,
      null
    ],
    "last_move": {
      "player_id": "player-001",
      "position": 4,
      "symbol": "X"
    },
    "next_turn": "player-002"
  }
}
```

# 3.6 ERROR

### Direction

**Server → Client**

### Purpose

Reports an invalid operation without terminating the TCP connection or crashing the game server.

### Schema

```json
{
  "type": "ERROR",
  "game_id": "string",
  "player_id": "server",
  "payload": {
    "code": "string",
    "message": "string"
  }
}
```

### Error Codes

| Code                | Meaning                                              |
| ------------------- | ---------------------------------------------------- |
| `INVALID_JSON`      | Received data was not valid JSON.                    |
| `INVALID_MESSAGE`   | Message structure or type was invalid.               |
| `OUT_OF_TURN`       | Player attempted to move when it was not their turn. |
| `INVALID_POSITION`  | Position was outside `0-8`.                          |
| `OCCUPIED_POSITION` | Selected square was already occupied.                |
| `GAME_NOT_FOUND`    | Supplied game ID does not exist.                     |
| `NOT_PLAYER`        | Client is not a participant in the game.             |
| `GAME_OVER`         | Client attempted to move after the game ended.       |

### Example

```json
{
  "type": "ERROR",
  "game_id": "game-001",
  "player_id": "server",
  "payload": {
    "code": "OUT_OF_TURN",
    "message": "It is not your turn."
  }
}
```

An error does **not** terminate the connection.

The client remains in the current game state and may attempt another valid operation.

# 3.7 GAME_OVER

### Direction

**Server → Client**

### Purpose

Notifies both players that the game has ended.

A game can end because a player wins, the game is a draw, or a player disconnects.

### Schema

```json
{
  "type": "GAME_OVER",
  "game_id": "string",
  "player_id": "server",
  "payload": {
    "result": "string",
    "winner": "string|null",
    "reason": "string",
```

### Fields

| Field    | Type        | Description                             |
| -------- | ----------- | --------------------------------------- |
| `result` | string      | `"WIN"`, `"DRAW"`, or `"FORFEIT"`.      |
| `winner` | string/null | Winning player ID or `null` for a draw. |
| `reason` | string      | Why the game ended.                     |
| `board`  | array       | Final board state.                      |

# 3.8 DISCONNECT

### Direction

**Client → Server**

### Purpose

Gracefully informs the server that the client intends to leave the game and close the connection.

### Schema

```json
{
  "type": "DISCONNECT",
  "game_id": "string",
  "player_id": "string",
  "payload": {
    "reason": "string"
  }
}
```

### Example

```json
{
  "type": "DISCONNECT",
  "game_id": "game-001",
  "player_id": "player-001",
  "payload": {
    "reason": "CLIENT_EXIT"
  }
}
```

The server processes the message, performs the appropriate game cleanup, and closes the TCP connection.

If the client disconnects while a game is active, the remaining player wins by forfeit.

# 4. TCP Stream Packet Framing

## 4.1 Framing Mechanism

TCP provides a reliable byte stream, not a message-oriented protocol.

Therefore, the server and clients **must not assume that one `recv()` call corresponds to exactly one JSON message**.

This protocol uses **newline-delimited JSON (NDJSON)**.

Each JSON message must:

1. Contain exactly one JSON object.
2. Contain no newline characters inside the JSON object.
3. End with `\n`.

For example:

```text
{"type":"CONNECT","game_id":"pending","player_id":"player-001","payload":{"player_name":"Alice"}}\n
```

---

## 4.2 Multiple Messages in One TCP Read

TCP may combine multiple application messages into one received byte sequence.

For example, the receiver might receive:

```text
{"type":"CONNECT","game_id":"pending","player_id":"player-001","payload":{"player_name":"Alice"}}\n{"type":"MOVE","game_id":"game-001","player_id":"player-001","payload":{"position":4}}\n
```

This contains **two separate protocol messages**.

The receiver must split the byte stream at each newline character.

---

## 4.3 Fragmented Messages

TCP may also split one application message across multiple `recv()` calls.

For example:

### First `recv()`

```text
{"type":"MOVE","game_id":"game-001","player_id":"play
```

### Second `recv()`

```text
er-001","payload":{"position":4}}\n
```

The receiver must accumulate both chunks before attempting to parse the JSON object.

---

# 5. Receiver Framing Algorithm

Each socket maintains a persistent receive buffer.

Conceptually:

```text
buffer = ""

while connection_is_open:

    data = recv()

    if data == 0 bytes:
        connection_closed = true
        break

    buffer += decoded_data

    while "\n" exists in buffer:

        message, buffer = split_at_first_newline(buffer)

        if message is empty:
            continue

        parse message as JSON
        process message
```

The important rule is:

> Data received from TCP must be accumulated until a complete newline-delimited JSON message is available.

The receiver must also preserve any bytes following the first newline because they may represent another complete message or the beginning of another fragmented message.

# 6. TCP Connection Lifecycle

## 6.1 Normal Connection

The normal connection sequence is:

```text
Client
  |
  | TCP connect()
  v
Server
  |
  | CONNECT
  v
WAITING_FOR_PLAYERS
  |
  | GAME_START
  v
GAME
  |
  | DISCONNECT
  v
CLEANUP
  |
  | TCP FIN
  v
Connection Closed
```

---

## 6.2 Graceful Application Disconnect

A client that intentionally exits should send:

```json
{
  "type": "DISCONNECT",
  "game_id": "game-001",
  "player_id": "player-001",
  "payload": {
    "reason": "CLIENT_EXIT"
  }
}
```

The server then:

1. Processes the disconnect.
2. Removes the client from the active game.
3. If a game is active, awards the opponent a forfeit win.
4. Sends `GAME_OVER` to the opponent when applicable.
5. Cleans up the game state.
6. Closes the client's socket.

The TCP connection is then terminated using the normal TCP FIN process.

---

# 7. Abrupt Connection Termination

The server must also handle clients that disappear without sending `DISCONNECT`.

Possible causes include:

* Client process crashes.
* Computer loses network connectivity.
* Client machine shuts down.
* TCP connection is reset.
* Network path fails.

The server must treat these events as disconnects.

### TCP Reset

Socket operations may raise:

```text
ConnectionResetError
```

The server should catch the exception and perform the same game cleanup as an unexpected disconnect.

### Send Failure

If the server attempts to send data to a disconnected client, the operation may raise:

```text
BrokenPipeError
```

The server must catch this exception and clean up the client's session rather than crashing the entire server.

---

# 8. TCP 0-Byte EOF Handling

A TCP `recv()` operation returning zero bytes indicates that the peer has performed an orderly shutdown.

For example:

```python
data = client_socket.recv(4096)

if len(data) == 0:
    # Client closed the TCP connection.
    handle_disconnect(client)
```

The server must **not continue calling `recv()` indefinitely** after receiving zero bytes.

The connection should instead be removed from the active connection list and its game state should be cleaned up.

---

# 9. Required Socket Exception Handling

A server implementation should protect socket operations with exception handling similar to:

```python
try:
    data = client_socket.recv(4096)

    if len(data) == 0:
        handle_disconnect(client)

except ConnectionResetError:
    handle_disconnect(client)

except BrokenPipeError:
    handle_disconnect(client)
```

The exact implementation language may vary, but the application protocol requires these conditions to result in session cleanup rather than server failure.

---

# 10. Game State Rules

The server is authoritative for all game state.

A Tic-Tac-Toe board contains nine positions:

```text
0 | 1 | 2
--+---+--
3 | 4 | 5
--+---+--
6 | 7 | 8
```

Valid winning combinations are:

```text
[0, 1, 2]
[3, 4, 5]
[6, 7, 8]

[0, 3, 6]
[1, 4, 7]
[2, 5, 8]

[0, 4, 8]
[2, 4, 6]
```

The server checks these combinations after every valid move.

# 11. Move Processing

When the server receives a `MOVE` message, it performs the following sequence:

```text
Receive MOVE
     |
     v
Is game active?
     |
    No ---> ERROR: GAME_OVER
     |
    Yes
     |
     v
Is sender a player?
     |
    No ---> ERROR: NOT_PLAYER
     |
    Yes
     |
     v
Is it sender's turn?
     |
    No ---> ERROR: OUT_OF_TURN
     |
    Yes
     |
     v
Is position 0-8?
     |
    No ---> ERROR: INVALID_POSITION
     |
    Yes
     |
     v
Is position empty?
     |
    No ---> ERROR: OCCUPIED_POSITION
     |
    Yes
     |
     v
Place player's symbol
     |
     v
Check winner
     |
     +---- Winner ---> GAME_OVER
     |
     +---- Board full ---> GAME_OVER / DRAW
     |
     +---- Otherwise ---> STATE_UPDATE
```

Invalid moves never modify the board.

Invalid moves also do not terminate the TCP connection.

# 12. Protocol Summary

| Message        | Direction       | Purpose                                             |
| -------------- | --------------- | --------------------------------------------------- |
| `CONNECT`      | Client → Server | Join the game lobby                                 |
| `LOBBY_WAIT`   | Server → Client | Inform client that it is waiting for another player |
| `GAME_START`   | Server → Client | Assign player role and start game                   |
| `MOVE`         | Client → Server | Request a board move                                |
| `STATE_UPDATE` | Server → Client | Broadcast updated board                             |
| `ERROR`        | Server → Client | Report invalid operation                            |
| `GAME_OVER`    | Server → Client | Report win, draw, or forfeit                        |
| `DISCONNECT`   | Client → Server | Gracefully leave the game                           |

This protocol provides deterministic message boundaries, explicit JSON schemas, server-side validation, graceful shutdown, abrupt disconnect handling, and enough information to implement a complete two-player Tic-Tac-Toe application over TCP.
